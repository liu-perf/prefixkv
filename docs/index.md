# prefixkv — 前缀缓存省下来的，有多少是缓存的功劳

前缀缓存的命中率**主要是流量的性质**，不是缓存的性质。所以这个库拒绝单独报一个命中率：
每个 prompt token 都被归入四个桶之一——**从缓存拿到的 / 被驱逐或占用挤掉的 / 被块粒度
丢掉的 / 任何缓存都救不了的**——而且四者相加精确等于总数。

零依赖，不需要 tokenizer、不需要模型、不需要 GPU。输入是 CSV，输出是 token 计数。

```console
$ prefixkv run tests/traces/EXAMPLE_agent.csv --capacity-blocks 96 --audit
hit: [info] 63088 tokens (79.5% of prompt)
capacity_loss: [info] 1536 tokens (1.9%) -- available at this block size but evicted or pinned
alignment_loss: [info] 492 tokens (0.6%) -- reusable at byte granularity, thrown away by block granularity
novel: [info] 14250 tokens (18.0%) -- no cache of any granularity could serve these
partition: [ok] the four buckets sum to 79366 prompt tokens exactly
capture: [info] 97.6% of the reuse available at this block size
structural: [info] block granularity allows 99.2% of this traffic's total reuse
```

## 三个发现

### ① 同样的内容，只换一个顺序，命中率归零

`EXAMPLE_system_prompt.csv` 和 `EXAMPLE_shared_last.csv` 的段**逐字节相同**——一个
180 token 的共享前缀加 160 个各不相同的问题，两边都是 37 803 个 prompt token。唯一的
区别是后者把共享部分放在了**独有部分的后面**。

| 轨迹 | prompt token | 命中 | 无法复用 |
|---|---|---|---|
| `EXAMPLE_system_prompt.csv` | 37 803 | **74.0%** | 24.3% |
| `EXAMPLE_shared_last.csv` | 37 803 | **0.0%** | 100.0% |

前缀缓存复用的是**前缀**。在共享部分前面放任何独有内容，那些 token 就永远够不着了——
而且**没有任何缓存配置能救回来**：加内存没用，改块大小没用。这是 prompt 拼装里一行的
改动，值 74 个点。

**需要工具的原因是：两次运行报出的命中率，和「这段流量根本没有共享」时看到的一模一样，
都是 0%。** PK001 就是用来区分这两件事的，而且它点名到请求和 token 数：

```console
r0000: [violation] PK001 180 tokens of reusable segments sit behind the single-use
segment USR:q0000; ... Move the shared part first.
```

### ② 命中率主要是流量，所以它不构成对缓存的任何主张

同一个缓存、同一个块大小、无限内存，七条轨迹：

| 轨迹 | 命中 | 对齐损失 | 无法复用 | **capture** | structural |
|---|---|---|---|---|---|
| `EXAMPLE_fewshot.csv` | 90.0% | 0.0% | 10.0% | **100%** | 100% |
| `EXAMPLE_agent.csv` | 81.4% | 0.6% | 18.0% | **100%** | 99% |
| `EXAMPLE_system_prompt.csv` | 74.0% | 1.7% | 24.3% | **100%** | 98% |
| `EXAMPLE_multiturn.csv` | 72.1% | 1.2% | 26.7% | **100%** | 98% |
| `EXAMPLE_tiny.csv` | 53.2% | 5.8% | 41.0% | **100%** | 90% |
| `EXAMPLE_no_sharing.csv` | 0.0% | 0.0% | 100.0% | n/a | n/a |
| `EXAMPLE_shared_last.csv` | 0.0% | 0.0% | 100.0% | n/a | n/a |

**命中率从 0% 跨到 90%，而 capture 处处是 100%。** 每一次运行都把能拿的都拿到了，
差异全部来自流量。所以：

- `capture = 命中 / 块对齐上限`——**唯一一个关于缓存的数字**；
- `structural = 块对齐上限 / 字节粒度上限`——块粒度在这段流量上的代价，也不关缓存的事。

拿两个缓存在不同流量上的命中率排名，排的是流量。`compare()` 会直接报错而不是默默照做。

### ③ 容量是悬崖，不是斜坡

`EXAMPLE_agent.csv`，16 token 一块，同时只有一个请求在跑：

| 缓存块数 | 命中 | 容量损失 | capture |
|---|---|---|---|
| 32 | **0.0%** | 81.4% | 0.0% |
| 48 | 52.9% | 28.5% | 65.0% |
| 64 | 65.5% | 15.9% | 80.4% |
| 96 | 79.5% | 1.9% | 97.6% |
| 256 | 81.4% | 0.0% | 100.0% |

**在「一个 prompt 刚好装得下」这一点以下，命中率精确等于零**——插进去的每个块，都在下
一个请求够到它之前被驱逐了。一个朝零线性外推的容量规划会完全错过这个断点。

并发花的是同一块内存，所以它和缓存直接竞争。同一条轨迹、256 块：

| 同时在跑 | 命中 | capture | 被 pin 阻塞的驱逐 |
|---|---|---|---|
| 1 – 8 | 81.4% | 100.0% | 0 |
| 16 | 77.8% | 95.5% | 14 918 |
| 32 | 68.0% | 83.5% | 21 451 |

块数换算成显存由 `capacity_blocks_for` 做，不猜任何一项：Llama-3.1-8B 形状的 GQA 解码器
跨 32 层，每 token 占 131 072 字节，所以 16 token 一块是 **2.0 MiB**，1 GiB 缓存是
**512 块**。

## 能失败的那条检查

四个桶是一个**划分**，而且和单条时间线上的 `L = λW` 不同，这条恒等式**不是算术保证的**：
`hit` 来自缓存自己的计数器，两个上限来自对轨迹 `segments` 列的算术，**完全不碰缓存代码**。

第二条路走得通，是因为一个请求是一串**具名段**：

```text
# LEN SYS:assistant_v3=180
request_id,arrival_s,segments,output_tokens
r0000,0.418697,SYS:assistant_v3|USR:q0000,163
```

不同段名占用互不相交的 token id 区间，所以两个请求永远不可能共享一个段的**一部分**——
两个请求的最长公共前缀**精确等于**它们共同前导段的长度之和。**轨迹自己声明了它的复用
上限，写在一列人能读懂的文本里**，`prefixkv ceilings` 算它的时候一个缓存都不需要。

交叉验证：上限公式必须等于真实的链式哈希块缓存在无限内存下达到的值。
**7 条轨迹 × 5 个块大小 = 35 个配置，零失配**，而两边不共享任何代码。

## 调任何参数之前该知道的两个机制

**只有完整的块能被缓存。** L 个 token 的共享前缀产出 `L // block_size` 个可复用块，
余数每次都要重算。180 token 的系统 prompt 配 16 token 的块，每个请求永久浪费 4 个
token——这条轨迹上一共 640 个。块大小 64 时是 52 个。

**最后一个 token 永远不可能命中**，因为模型必须在某个东西上跑一遍才能产出 logit，而且
之后缓存长度还得保持块对齐。按这个顺序：64 token 的 prompt 配 16 token 的块得 63，向下
取整到 48。**一个正好四块长的 prompt，只能复用三块。**

块大小就是在这两者之间权衡。`EXAMPLE_multiturn.csv`，无限内存：

| 块大小 | 命中 | 对齐损失 | structural |
|---|---|---|---|
| 1 | 73.3% | 0.0% | 100.0% |
| 16 | 72.1% | 1.2% | 98.4% |
| 64 | 67.8% | 5.5% | 92.5% |
| 256 | 51.5% | 21.7% | 70.3% |

## 五条规则

| 规则 | 抓什么 |
|---|---|
| **PK001** | 可复用的段被压在单次使用的段后面，于是永远够不着 |
| **PK002** | 共享前缀不是块大小的整数倍，以及这代价多大 |
| **PK003** | 流量本身就没有共享，前缀缓存根本不是这里的杠杆 |
| **PK004** | capture 低于报告门限，说明限制在容量或占用 |
| **PK005** | logit 规则带来的整块损失，落在约 1/`block_size` 的 prompt 上 |

`test_every_rule_fires_somewhere_and_stays_quiet_somewhere` 断言每一条**既响过也静过**。
一条永远响的规则和一条永远不响的规则，一样没用。

## 这个工具做不到什么

写在这里是因为它们**到今天仍然开着**。

1. **没有调度器。** 并发只通过一个旋钮进入——`--concurrency N` 把最近 N 个在跑请求的块
   钉住——除此之外没有成本模型也没有步进循环。那是另一个工具的事，在这里重做一遍只会
   得到两个各标定一半的模型。

   这一条已经**对着真引擎量过**，不是一个形容词。把每条轨迹重放给 `vllm serve`，
   和 `vllm:prefix_cache_hits` 对账，3 个缓存大小 × 3 个并发 × 6 条轨迹：

   - **串行时模型是精确的。** `--concurrency 1` 下模拟命中与真引擎**逐 token 相等**，
     六条轨迹全部如此，缓存从 160 块（紧到 agent 轨迹反复驱逐）到 4096 块都成立。
   - **并发下它偏悲观**，紧缓存 + `--concurrency 32` 时相对上限最大低估 **40.9%**。
     pin 窗口把最近 N 个请求的块挡在驱逐之外；真引擎请求跑完就释放，块回到 free 队列
     但仍留在缓存里，所以它保住了这个模型扔掉的那部分复用。
   - 那个 40.9% 是**模型误差的上界而不是误差本身**：两个"并发"不是同一个量——
     这里是"钉住 N 个请求的块"，实验里是"允许 N 个请求同时在途"，而真引擎同时驻留的
     远少于 N。要把两者分开需要一个调度器视角，那正是这条 Limit 的意思。
2. **只有 LRU 一种驱逐。** 真实引擎还有引用计数的细节、未缓存块按 LIFO 复用以提升局部性、
   以及块大小超过哈希粒度时的部分块技巧。这里只建模了「在未被 pin 的块里选最久未用」。
3. **段是原子的。** 两个请求要么共享一个段要么不共享。真实流量有段内部分重叠——改过一版
   的系统 prompt、换了说法的问题——这个库表达不了。它让上限变得精确，也让流量模型变粗。
4. **所有轨迹都是合成的。** 这里每一个数字都测在生成的流量上，而它的共享结构是我选的。
   机制可迁移，百分比是这七个文件的性质。
5. **除前缀外没有别的共享。** 没有滑动窗口、没有选择性驱逐、没有压缩、没有磁盘或 CPU 分层。

## 姊妹项目

- **blocktax** — 这个权衡的**另一半**。`docs/blocks.md` 里那张块大小表明说了小块的代价
  「这个库一个都没测」，blocktax 把它测了：块表散布时块大小 1/2/4 比 16 慢 1%–2.4%，
  8 及以上互相不可分辨，而且代价来自**间接寻址不是 tile 尺寸**。
  两个项目一起才是完整的交易曲线，单独任何一个都只是一列。
- **kvsched** — 同一张卡上，调度和 KV 分页的决定值多少。
- **vLLM `kv_cache_token_usage_perc`** — 一个提给上游的指标：按块计数的占用率
  看不见部分块里的空槽，短 prompt 下能差 30 个百分点。
